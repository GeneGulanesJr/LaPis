# Plan: Refactor Pi Extension into Thin Composition Root (Issue #75)

## Branch Strategy

- **Base branch**: `v1.0.0` (already exists on remote)
- Checkout `v1.0.0` locally, all work committed there

## Goal

Refactor `extensions/memory-layer/index.ts` (1805 lines) into a thin composition root with separated host, hooks, tools, and formatter modules — preserving all runtime behavior and backward compatibility.


### Step 16: Rewrite `index.ts` as Composition Root

The new `index.ts` becomes a thin orchestrator (~50-80 lines):

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { state } from "./state";
import { ensureNativeModules } from "./host/native-health";
import { mem, memCmd, memStreaming } from "./host/memory-client";
import { detectProject } from "./host/project-detector";
import { getKnownRepos, isRepoStale, isCodeFile } from "./host/repo-cache";
import { registerSessionStart, registerSessionCompact, registerSessionShutdown } from "./hooks/session-lifecycle";
import { registerBeforeAgentStart, registerContextReminder } from "./hooks/context-injection";
import { registerPassiveCapture } from "./hooks/passive-capture";
import { registerToolGuardrails } from "./hooks/tool-guardrails";
import { registerTrustSync } from "./hooks/trust-sync";
import { registerMemoryTools } from "./tools/memory-tools";
import { registerCodeTools } from "./tools/code-tools";
import { registerDocTools } from "./tools/doc-tools";

export default function (pi: ExtensionAPI) {
  const deps = {
    state, ensureNativeModules, mem, memCmd, memStreaming,
    detectProject, getKnownRepos, isRepoStale, isCodeFile,
  };

  // Hooks
  registerSessionStart(pi, deps);
  registerSessionCompact(pi, deps);
  registerBeforeAgentStart(pi, deps);
  registerToolGuardrails(pi, deps);
  registerContextReminder(pi, deps);
  registerPassiveCapture(pi, deps);
  registerTrustSync(pi, deps);
  registerSessionShutdown(pi, deps);

  // Tools + Commands
  registerMemoryTools(pi, deps);
  registerCodeTools(pi, deps);
  registerDocTools(pi, deps);
}
```

Each registration function wraps its hook/tool registration in a try-catch so a failure in one adapter (e.g., doc-tools) does not prevent others from registering.

## Key Design Decisions

1. **Shared state singleton** (`state.ts`) rather than passing state through every function. This avoids deep prop drilling while keeping state explicit and testable (tests can reset `state` between cases).

2. **Deps injection pattern** — Each hook/tool registration function takes a `deps` object. Tests can provide mock implementations. This follows the existing project convention (services use `deps: { sqlJson, sqlRun }`).

3. **Error isolation** — The composition root wraps each registration in try-catch so one module's failure doesn't crash the entire extension. This directly addresses the blast-radius concern from the issue.

4. **No tsconfig changes** — The extension is already TypeScript and loaded by Pi's runtime. The new `.ts` files follow the same pattern.

5. **Trust sync split** — The `tool_result` handler currently does two things: auto-save edits AND git-triggered trust sync. These are split into `passive-capture.ts` and `trust-sync.ts` respectively, each registering their own `tool_result` listener.

## Risk Mitigation

- **Preserve exact behavior**: No logic changes during extraction — only file moves and import adjustments
- **Incremental extraction**: Each step produces a working state; if something breaks, bisect to the specific extraction
- **Existing tests as safety net**: The 30 existing tests verify the backend behavior remains unchanged
